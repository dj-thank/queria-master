# 検索性能・メモリ設計

## 結論

全量スナップショットの5,823,039法人をDuckDB本体に保持したまま、読み取り専用SQLite sidecarへFTS5 trigram索引とカテゴリ索引を構築する。`search --fast` はこの索引を使い、結果の安定ソートを省略して早く返す。索引には原本DBのrefresh_id、サイズ、mtimeを記録し、通常の検索開始時はDuckDBを開かずに統計情報だけを比較する。古い形式の索引や統計不一致時だけDuckDBのrefresh_log検証へフォールバックする。カテゴリ先頭経路は、同一法人が大分類行と中分類行を持つ場合でも重複行を返さないよう、カテゴリ索引から `DISTINCT doc_id` を経由して法人テーブルへ結合する。これにより `LIMIT 1000` はカテゴリ行数ではなく、最大1,000法人を意味する。

索引に格納する検索列は社名、所在地、事業概要、事業種目、企業URLである。FTSは `detail=full` の連続フレーズ照合を使うため、三文字以上の日本語キーワードは `LIKE` の後処理なしで検索でき、`ソフトウェア開発` と `ソフト開発ウェア` のような近似文字列を混同しない。

## 全量実測

対象は `all-public` の同一更新ID `e49dbd7e-e9ad-4fff-9ae1-7c68d7f9db2a`。検索索引はSQLite約2.4GB、FTS tokenizerはtrigram、ベンチマークは同一プロセスでウォームアップ2回後に5回実行した。計測値は検索処理だけで、Python起動時間やCSVのディスク書き込みを含まない。

現行onefile EXEの総時間は別測定する。`ソフトウェア` の10/100/1000件CSV出力は、プロセス起動から完了までおおむね1.7〜2.1秒だった。この差はFTSが遅いことを意味せず、onefile展開、Python起動、結果整形、ファイル出力を含むためである。測定値は `work/bench/exe_baseline.json` に保存する。検索索引の整合性確認はDBサイズとmtimeを先に比較し、一致時はDuckDBを開かない。

速度優先の利用者向けには `daemon` とデスクトップEXEを用意する。常駐モードでは索引接続を一度だけ開き、JSONLの検索応答は列名1回＋値配列で返す。GUI版は検索workerと表示threadを分け、100行単位でTreeviewへ反映する。常駐検索の取得時間とGUI初回描画時間は別々に計測する。

| ケース | 返却件数 | p50 | 最大 |
|---|---:|---:|---:|
| `ソフトウェア`, `--fast` | 1,000 | 9.563 ms | 9.647 ms |
| `株式会社`, `--fast` | 100 | 0.532 ms | 0.550 ms |
| 東京都 × 大分類G, `--fast` | 1,000 | 8.434 ms | 10.793 ms |
| 東京都 × 中分類39, `--fast` | 8 | 0.063 ms | 0.073 ms |
| 東京都, `--fast` | 1,000 | 2.821 ms | 2.945 ms |
| `ソフトウェア`, 安定ソート | 1,000 | 21.785 ms | 22.067 ms |

常駐CLI daemonの0.8.0基準EXEでは、同じ `ソフトウェア` 1,000件がonefileでroundtrip p50 18.074ms、onedirで13.023msだった（各5回、ウォームアップ2回）。修正版EXEの再起動はこのホストのアプリケーション制御ポリシー WinError 4551 でブロックされたため、最新EXEの合格値とは区別する。現行ソースdaemonの再計測はroundtrip p50 14.398ms、server p50 10.751msだった。GUI版もDBと索引を一度だけ開き、検索workerから100件ずつTreeviewへ渡す。検索取得が速くても、初回GUI描画とCSV書き込みは別途計測する。GUI実行の最終ゲートは配布先Windowsの署名・実行制御環境で行う。

短い検索語は別扱いである。`--fast` では法人名の前方一致インデックスを使い、`--fast`なしでは従来どおり社名・住所・概要・連絡先の部分一致を行う。前者は速度優先、後者は網羅性優先の契約である。

`--fast` のFTS結果は全文検索の自然な索引順であり、従業員数・資本金・社名順を保証しない。営業リストの再現性や並び順が必要な場合は安定ソートを使う。1回に数万件以上をCSVへ書き出す場合は、検索自体が速くても出力先のI/Oが支配的になる。

## メモリ設計

検索索引の構築時はDuckDBの一時メモリ上限を1GBに設定し、原本からCSVをストリーミングしてSQLiteへバッチ投入する。今回の全量構築で観測したPythonプロセスのprivate memoryは最大約2.2GBだった。検索時はSQLiteをimmutable/read-onlyで開くため、全法人のテキストをPythonオブジェクトへ展開しない。

埋め込みは全法人へ自動適用しない。384次元のfloat32を5,823,039件へ密に置くだけで約8.9GiBとなり、モデル計算・更新時間・検索時のメモリ負荷が大きい。代わりに `build-semantic-index` は説明文などのあるtext-rich法人を対象に `float16` のメモリマップへ保存し、`semantic-search --candidate-keyword` でFTS候補を先に絞る。ベクトル走査は50,000件単位で行うため、候補数を抑えた場合の追加メモリも限定される。

埋め込みモデルとNumPyは任意依存であり、モデルのダウンロード・利用条件は利用者が確認する。キーワード・カテゴリ検索はこれらをインストールしなくても利用できる。
