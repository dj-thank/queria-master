## 結論

- Libraryで確認できたfile metadata
- ZIPと同時生成された展開済みsource・reportから復元できた内容
- GitHub履歴との照合
- byte取得不能のため未確認の事項

ZIP名やcompanion reportだけを根拠に「実ZIPを検証済み」とは扱いません。

## `integrated-code` companion source

ZIPと連続して保存されていた次の完全textを復元しました。

- `queria_master.py` (`APP_VERSION = "2.0.0"`)
- `schema.sql`
- `build-windows.ps1`
- `README.md`
- `DATA_AUDIT.md`

この系統の独自価値は、Queria公開DuckLakeではなく、公式gBizINFO Basic CSVとローカルHojinjoho JSON ZIPを直接読み、法人基本と活動をDuckDBへ正規化する経路です。一方、復元sourceは既存DBを直接削除・再構築し、途中失敗時に部分状態を残し得るため、そのままcanonicalへ上書き統合しませんでした。

現行コードには、この価値だけを再設計した`import-gbiz-archive`を追加しました。入力は新規の非canonical staging DuckDBに限定し、resource limit、path/metadata preflight、JSON payload検証、hash、transaction、no-clobber公開を適用します。stagingからcanonicalへのpromotionは自動化していません。

companion `DATA_AUDIT.md`は、元Hojinjoho archiveについて次を主張します。

- SHA-256 `4617dd5ae7f31f8e1a6201295d95516e21b84e06ef37c949145119b58f520a4e`
- ZIP 379,025,154 bytes
- JSON member 45
- uncompressed 5,786,410,982 bytes
- companies 447,900
- industry `G` 7,948 companies

元ZIP本体を取得できなかったため、これらは現importerの実測値でも、こちらで全byteを検証した結果でもありません。元ZIPを再取得できた場合は、まずarchive SHA-256を照合し、その後にstaging import、member hash、件数を再検証します。

## 旧版と不採用候補

`queria-master(3).zip`のcompanion sourceはQueria Master 0.3.0で、Queria CLI→Parquet→DuckDB、read-only remote SQL、atomic refresh、manifestという現行系の旧lineageです。現行Gitの方が包括的なため、旧sourceで上書きしません。

`queria-duckdb-native-complete.zip`のcompanion build reportは、DuckDB CLI downloadがDNS解決失敗で停止し、statusも`building`、errors配列ありでした。「complete」というfile名だけでは完成証拠にならないため採用しません。

`realdata`は内部byteを取得できません。後続`integrated-code`の説明と保存順から中間成果物と推測できますが、内部diffで証明できないため推論としてのみ扱います。

## 再取得時の手順

1. expected name・bytes・known SHA-256を照合する。
2. ZIP slip、absolute path、duplicate path、symlink、special entryを拒否して隔離展開する。
3. normalized relative pathごとにsize、mode、SHA-256を記録する。
4. source tree、manifest、report、内部Git metadataの有無を比較する。
5. Hojinjoho元ZIPは`import-gbiz-archive`で別stagingへ取り込み、companion値と独立照合する。

取得不能のZIP、Library原本、GitHubの既存branch/releaseは変更していません。
